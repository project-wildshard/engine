# TS11: the last case-level load flakes

> Written by: Claude (opus-testspeed2)

TEST-SPEED TS11 (meta `docs/plans/TEST-SPEED-PLAN.md`): flakes that only show under a loaded gate or a cold hosted
worker. Each fix keeps the case's caps and assertions.

## grid-tap-paint: the error modal's cold chunk

`src/client/engine/boot/grid-tap-paint.test.ts` > "RL4 / MF3: a slow boot shows nothing…" went red once in main
ci 43076662972: "expected '' to contain 'failed to start'" after 1016 ms, and passed 3 of 3 alone.

The case's last step is `guardBoot`'s second rejection, which opens the error modal through a lazy
`import('../ui/ErrorModal')` (stuck.ts `showFailure`). That module pulls in the app runtime, strings, terrain and
the error reporter. `vi.waitFor` gives the modal 1 s of real time. On a hosted worker whose transform cache missed,
the import alone took longer, so the modal had not opened when `waitFor` gave up.

Proof: a copy of the old file with a planted 1.2 s (real time) delay on that import fails the same way ("expected
'' to contain 'failed to start'", 1007 ms); the fixed copy passes. The fix loads the modal's module once in the
file's `beforeAll`. The case still goes through the same lazy `import()` and every assertion, and `waitFor` keeps
its 1 s. Stress: 36 of 36 green, cold module cache (`--fsModuleCache=false`), six at a time beside 16 busy loops,
load 20-28 on the 18-core Mac.

## A warning about the stress runs

The first proofs below ran nice-0 busy loops beside the tests to raise the load. Vitest's local workers and their
children run at nice 10 (`vitest.config.ts`, BUILD-SPEED 1.2), so those loops starved every other lane's tests. Two
of opus-wire's pre-push runs failed during them (13:53 and 14:04 Cancún: net-fuzz, physics headless, the lease
fixture below). From then on this lane proves things at the machine's own load only.

## FL20: net-fuzz's hostile Nalati case

The case gets 10 s. Phases at load 49 on the Mac: product read 0.35 s, room and resident 2.4 s, 120 hostile ticks
1.1 s, the save 2.2 s (a 13 MB snapshot), the restore 1.3 s. That is about 3 CPU-s, spread out: deflate 0.31,
`encodePhysicsReferences` 0.30, two resident builds 0.58 each (a cold Ajv compile 0.29 in the first), no single
hot spot TS4 has not already worked on.

What changed: the five fuzzed products are read in `beforeAll`. Every later case already shared them, so the file
does the same work; the case's 10 s now times the room, the ticks, the save and the restore. Paired runs, old and
new copies side by side at load 52-58: 7.5 / 9.3 / 11.2 s → 7.2 / 8.7 / 10.2 s, about 7 % faster.

Measured note, as TS11's done-when allows: the case only fails above a 1-minute load of about 50 on the 18-core Mac
(4 of 12 over 10 s at load 52-58; none at loads up to 35, where it takes 2.2-3.9 s). Hosted, the whole file takes
12-21 s for 13 cases (33 runs on 11-11), the Nalati case about 30 % of that, and it has not failed in any hosted run
with shard reports this week.

## FL23: Driftwood's worker case

The case gets 10 s. At load 37: the worker's start 2.25 s (its own thread loading 528 modules, 8.7 MB of source:
0.9-1.5 s before the first module body runs, then the asset recheck 0.3 s, the product and the resident), the
parent's resident 0.2 s, the worker's 300 ticks 0.4 s, the parent's 300 ticks 0.13 s, the final save 0.2 s.

What changed: the parent builds its resident while the worker starts, and steps its 300 ticks while the worker runs
its tape, instead of after. Same owners, inputs, ticks, assertions and 10 s. Paired runs: 4.79 → 4.42 s median at
load 10-25, 12.4 → 11.2 s at load about 50.

Measured note: the case fails only above a load of about 45-50 on the Mac. Hosted, the file takes 6-13 s for 3
cases and has not failed this week. A compile cache would cut the worker's module load by 40 % (0.94 → 0.54 s,
measured), but Node writes it only when a worker exits, and each Vitest run gets a fresh cache folder, so the one
worker in this file is always cold. Left as a TS6 note, not changed here.

## The lease-order fixture (coordinator, 11-11)

`test/mirror-lease-order-4.test.ts` runs `scripts/test_lease_order.py` partition 4/4. Its "unknown shell wrapper"
case failed in opus-wire's pre-push with "fixture synchronization timed out": the test waited 10 s for the preview
fixture's `preview.locked`. `wait_for` polled the marker only. When a fixture process exits early (a refusal, a
crash), the test kept polling for the full 10 s and then threw away the fixture's own error.

`wait_for` now also watches the processes it waits on. If one exits before it is ready, the test fails at once with
that process's exit code and output. A real early exit shows it: run from a script under `tmp/`, the fixture is
refused by the G670 caller guard, and the test now says "fixture exited 1 before it was ready: … G612/G670: mirrors
refuse a caller script under tmp/" in milliseconds instead of a bare timeout after 10 s. The 10 s cap stays for a
fixture that is still alive. 84 runs, 12 at a time: all green (36 at the machine's own load, 48 beside the busy loops).

## FL22: browser-escape's detached writer inventory

No new change: the root was found and fixed on 11-10 in `74224a35` ("collect native inventory atomically"). An
`execFile` timeout could destroy the pipes of a `ps` that had already exited when the worker stalled for 650 ms,
which gave an empty "successful" inventory and so the "Invalid native process inventory" row. The inventory now runs
synchronously with the same 500 ms and 5 s clocks, and on Darwin reads one kernel snapshot instead of `ps`. Since
then the case ("native cleanup drains a detached descendant writer…") passed in all 33 hosted runs with shard
reports on 11-11, and 18 of 18 on the Mac, six files at a time at the machine's own load (4.09-4.13 s).
