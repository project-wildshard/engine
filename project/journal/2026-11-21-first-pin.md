# First pin of a staging-only shard (meta MZ26)

- shard-pin.yml takes `first` (boolean); pin-shard.ts `--first` appends a slug engine never pinned to
  shardfiles.json and the pinned catalogue's shards, named from staging's catalogue row. Mossgate (and Mirror Salt)
  are staging-only, so `pins.ts refresh` never pinned them and budgets.yml never measured them. No placement or grid
  cell is added: production's catalogue has none for them. A local dry run (Mossgate rev 21) kept the catalogue,
  grid and pins tests green.

## The budgets run's measuring cell (later the same day)

The first budgets run after the pin (44949687876, for ci 44948577308) failed. Its phone Low frames booted
`?chunk=mossgate` against the pinned production catalogue, which has no placement or cell for a staging-only shard:
"Unknown built-in instance: mossgate". `phone-frames.mjs` now routes the page's HTML through `measuringCatalogue`, which
gives an unplaced pinned zone one cell east of the grid in that page's inlined catalogue, as `wildshard dev` does for its
one shard. A placed zone's page is unchanged. Red first in `test/phone-frame-budgets.test.ts`.

## The first baselines (mini-zones, later the same day)

Budgets run 44960274285, the first green run to measure both staging-first pins, booted them in a measuring cell. The
first try used [5, 0], and the catalogue refused it, because the grid holds cells up to 3 from the centre. The
measuring cell is now the nearest free one inside that bound. The run's eight `mossgate` and `mirror-salt` measures
went in with `cli.mjs record`, filtered to the two zones. A whole-run record would also have re-set 114 other zones'
baselines, 38 of them by more than 10%, on revisions that weren't this lane's.
