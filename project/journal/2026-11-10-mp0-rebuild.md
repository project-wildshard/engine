# MP0.1: a blank box to a serving host, in one script

MMO-PLAN MP0.1 wanted the VPS rebuildable from nothing. Phase 2's
setup.sh already owned the units, env files and Funnel routes, but it
assumed a Phase 1 that only ever existed as an older setup.sh run once
by hand. `scripts/vps/rebuild.sh` is that Phase 1 again, plus the parts
nobody had installed: it adds the NodeSource, Tailscale and Caddy apt
sources, installs Node 24, PostgreSQL 16, rclone, Tailscale and Caddy,
makes the users, PostgreSQL's socket-only settings, role and both saves
databases, the blank ops.env and the staged release key (read from
setup.sh, never a second copy), then runs harden.sh when VPS-HARDENING
writes it, then setup.sh, then the cook worker.

The hard stop is the first thing it does: a host with clawdbot's or
Matt's home, an `.openclaw`, the Ollama snap or Coolify's volume is
refused in both modes. That is today's VPS, so the script cannot touch it
before OPENCLAW-EXTRACT's OX10 and the Hetzner rebuild. No flag skips it.

Three things the proof found that reading would not have:

- The cook worker's unit (`scripts/cook-worker.service`, never
  installed) had `Environment=COOK_JOB_WRAP=["unshare",...]`. systemd
  strips those double quotes, so the worker died parsing its own wrap.
  The unit now lives in rebuild.sh, single-quoted, and the old file is
  gone. Its default port was 8791, which is staging's; it is 8792 now.
- Ubuntu 24.04 refuses unprivileged user namespaces to unconfined
  programs (`kernel.apparmor_restrict_unprivileged_userns=1`, read on the
  VPS). Every cook job runs in one. The worker gets its own copy of
  `unshare` and one AppArmor profile for that copy, and the unit checks
  the wrap once before it starts.
- Caddy's package starts a page on port 80. It is installed with its
  start refused, its default file replaced by a comment and disabled;
  VH9's real file is left alone on reruns.

`scripts/vps-rebuild-proof.sh` runs it in a throwaway container booting
systemd: --check, a run that waits for Tailscale, a stub `tailscale up`,
a run through Phase 2 that waits for cook.env, a run that installs and
starts the cook worker against a local catalogue of one pinned shard,
and a last run with no `doing` line. Both loopback ports then answer
from real servers that pulled the signed releases (production serial 4,
staging 69), the cook worker has cooked blender-template's index, and
nothing listens on 80 or 443. It runs on the Mac's arm64: under
Rosetta's amd64, systemd's own services (journald, tmpfiles, PostgreSQL)
fail, which says nothing about the script.

## The review's must-fixes

Codex (J206) found five. The worst was real and old: an env file's blank
`COOK_STORE_DIR=` reached cook-worker as an empty string, which picked a
folder store at the working directory over R2. Blank now means unset,
and the template leaves the row commented, so older tags are safe too.
Caddy's file was "default" if it mentioned `/usr/share/caddy` anywhere,
which a VH9 file could; now only dpkg's recorded bytes or this script's
own placeholder count. An existing `policy-rc.d` is put back after the
Caddy install, and a changed checkout or cook.env restarts the worker.
