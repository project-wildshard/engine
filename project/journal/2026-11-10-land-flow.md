# J240: land a plan worktree by fast-forward (DEV-SPEED DS21)

Jake, 2026-11-10: "An agent is in a work tree, it pushes. The pre-push
passes. He then checks the CI that runs on the branch in GitHub until it's
all good. And then he just merges… Merge fast forward only." Plan: meta
`docs/plans/DEV-SPEED-PLAN.md`, rows DS16 and DS21.

- `scripts/land.mjs` runs from a linked worktree on `plan/<slug>`: it rebases
  onto origin/main if behind, pushes the branch (the split pre-push runs),
  polls `gh api …/actions/runs?head_sha=` until `ci` and `ring-1` are both
  done for that exact SHA, then rebases again and pushes `HEAD:main` with no
  `+` and no force flag. A lost race means main moved: rebase and retry.
- The rerun rule after a rebase. If main hadn't moved, the exact green SHA
  lands. If it moved, the rebase was clean, no path changed on both sides and
  DS1 can select the plan's diff (related or docs), the proof is "carried": the
  main push runs the split gate on the rebased tree (`WS_PUSH_POST_CI=1`), and
  land watches main's hosted run afterwards. Anything else (shared paths, a
  harness, dependency or config change, a stale stamp, or an unknown path)
  pushes the rebased SHA to the branch again and waits for hosted CI.
- `ci.yml` and `ring-1.yml` now run on `plan/**` pushes too, cancelling a
  superseded plan SHA. On main, `scripts/ci-exact-reuse.mjs` finds the same
  workflow's green plan-branch run for the exact SHA and skips the jobs, so a
  landing never runs CI twice. If the lookup is unsure, the run goes full. A
  plan's history scan starts at its merge-base with main, not the zero SHA.
- Surprise: `check-push.mjs` given a zero remote SHA scans the whole history
  (over 180 s here), and git hands it a zero SHA on any new branch push. I
  passed that to opus-worktrees, who owns the hook.
- Tests: `test/land.test.ts` uses real git with a bare remote. The remote has
  a protect-main update hook, a post-receive log of pushed tips, and a fake
  `gh` that answers only for pushed SHAs. The cases: an exact fast-forward,
  main moving to disjoint paths (carried), main moving over the same file (a
  rerun), a race lost mid-push, red CI, a rebase conflict, refused force, a
  red pre-push, refused checkouts, and two worktrees landing at once.
- A Codex review (J206) found 4 MUSTs, all fixed before landing:
  - ring-1's `tests` job inherited the skip from a skipped `reuse` job. That
    could make main green without running its tests, so `reuse` now runs on
    every event.
  - Reuse now requires every blocking job, plus a `tests` matrix, to have
    passed on the latest attempt.
  - Reuse is refused if the quarantine or lift-pending exclusions changed
    since the branch run started.
  - land now pins the exact SHA it works on: a commit made during the CI
    wait stops it, and main gets `<sha>:refs/heads/main`, never HEAD.
- Also from the review:
  - A plan that changes `.github/` always reruns hosted CI after a rebase.
  - The branch rewrite is leased against the tip this worktree last pushed.
  - The lock is safe to take over when its owner is dead.
  - A failed `rebase --abort` stops land loudly.
- Recorded `test/land.test.ts` clocks (full and Ring 1) with
  `push-preflight.mjs timings`; the queue preflight refused it without them.
- Re-recorded the land test clocks after the PATH index fix changed its source.
