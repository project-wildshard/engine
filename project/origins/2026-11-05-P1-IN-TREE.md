## What P1 is

P1 makes every future repo boundary real **inside singleplayer**, enforced by lint, before any repo moves (J17).
No new repos are created. When P1 is done, each later move (P2–P6, [MOVES.md](MOVES.md)) is a mechanical copy.

**Where the work and the records go:**

- **Code changes land in singleplayer.** They follow singleplayer's own `AGENTS.md`:
  - `scripts/commit.sh` for every commit, with the scheduled push loop doing the pushing;
  - `heavy-lane.py` for builds and the full suite;
  - `browser-lane.sh` for browsers;
  - no worktrees or branches;
  - `Assisted-by:` trailers on commits.
- **Plan files never go in singleplayer** (Jake, 2026-11-04). This plan, its status and its decisions live only here.
  - Lanes record progress in [STATE.md](STATE.md) in this repo, not in a singleplayer `docs/plans/<plan>/STATE.md`.
  - Singleplayer commit messages cite the row id (for example `P1-E1`) so status here can be checked against
    singleplayer history.

Old row ids from the first draft: P1.1 → F1+F2, P1.2 → F3+F4, P1.3 → done ([ENGINE-CUT.md](ENGINE-CUT.md)),
P1.4 → E1–E4, P1.5 → C1, P1.6 → C2, P1.7 → S1, P1.8 → S2, P1.9 → C3, P1.10 → W1, P1.11 → T1.

### E5: listen server (J31)

Source and Unreal play singleplayer through a local server. We do the same: a third, **standalone** build target runs
the `server` build in a Web Worker, and the `client` talks to it over an in-process loopback. The app shell composes
the two; `client/` itself never imports `server/`. This keeps singleplayer shipping through the whole migration, and
it answers offline play (J16).

| Row | Work | Done when |
|---|---|---|
| E5.1 | **Replication design (J4).** Entity state declares which fields replicate and which are predicted, and snapshots and deltas are generated from those declarations. Start from `src/engine/sim/snapshot*.ts` and the tick commands in `src/sdk/tickProtocol.ts`. A design doc in this folder, reviewed by Jake before any code | Jake approves the design |
| E5.2 | **Loopback transport.** Server build in a Web Worker, client ↔ worker messages carrying input commands up and snapshots down, all behind a `Transport` interface that WebSockets can implement later. No network | A shard's server tick runs in the worker; the client receives snapshots |
| E5.3 | **Prediction and reconciliation** for the player's own character, using the `shared` movement (E4.1). Everything else is interpolated | Walking, jumping, swimming and the hoverboard feel the same as today on the phone baseline (singleplayer `bench`/phone goldens) |
| E5.4 | **Standalone target.** The build emits the client, the server, and standalone (client + server-in-worker). Production ships standalone until the MMO servers exist | Live deploy is the standalone target; Safari/phone numbers within today's budgets |

**Limit:** E5 builds the replication and loopback the MMO will use, but **no network transport, rooms, accounts or
persistence**. Those stay in Jake's MMO plan (G828, G1011).
